## Second pass — practical testing found two real bugs (commit 2f030fe, + touch fix)

The directive was to test practically, not just read code. Two real defects came out of running the
stream against the real SQL engine and reasoning about touch events:

1. **`mergeTaskEvents` crashed the chat on first paint.** `listTasks` returns task ROWS with no `events`
   field (only the `thread` op pairs a row with its events). The SSE stream can deliver the first `text`
   event before the thread op has paired them, so `task.events.map(...)` threw `Cannot read properties of
   undefined`. Guarded with `task.events || []`; `lastEventId` guarded too. Covered by
   `liveEvents.test.ts` ("starts a run whose row carries no events yet").
2. **A tap on the desktop clicked twice.** `onTouchStart` fires, then the browser synthesises a `click`;
   both called `clickScreen`, so every touch reached the desktop as a double-click (folders opened, text
   selected). Added a 700 ms `touchAt` ref guard in `GraphicalDesktop.tsx`.

## Session 3 (2026-11-06, later) — image/audio VQ collapse + native motion video (practical, on the ground)

### Root cause A: the image (and audio) VQ-VAE codebooks collapse → "gray / distorted" pictures
Measured directly: `VectorQuantizer.__init__` seeds the codebook with `nn.init.uniform_(-1/num_codes, 1/num_codes)`,
so at step 0 EVERY code sits within ~0.004 of the origin, while real encoder outputs sit ~1.0 away from it
(measured: `mean|z|`=0.139, `||z||`≈0.97). So every spatial location maps to whichever code is nearest the origin
and the codebook collapses. Measured on the synthetic set (256 codes, 40 epochs): **12/256 codes used**.
Fix, in `image_tokenizer.VectorQuantizer` and `audio_tokenizer.VectorQuantizer`:
`initialize_from_data()` (k-means seed from real encoder outputs) + `revive_dead_codes()` (re-seed idle codes),
wired into `train_image_tokenizer.train_vqvae` / `train_audio_tokenizer.train_vqvae` via new args
`data_init=True, revive_every=16, usage_decay=0.995, revive_threshold=0.5`.
Measured after fix (256 codes): **256/256 used AND recon-MSE 0.0148 vs the old 0.0162** (both better).
Key tuning result: reviving on EVERY step over-churns the codebook (256/256 but recon-MSE 0.0181); reviving
every ~16 steps with decay 0.995 is the setting that wins on BOTH usage and reconstruction.

### Root cause B: video was stitched stills → native motion-token video
The model now writes its OWN motion tokens (`motion_tokenizer.py`) after the keyframe image span; the clip is
decoded frame by frame through the flow. `sham_studio_media._video_result` / `_long_video_frames` produce real
MP4s. Verified on the ground: 24-frame clip → ffmpeg-decoded, mean |frame-to-frame| diff min 0.187 max 3.615
(0 would mean frozen stills) → frames really move; `media_quality.check_mp4` returns
`{duration_seconds: 2.0, frames: 16, decoded: True}` → PASSES the real-motion gate. Long clips verified:
48/240/600 frames → 6 s / 30 s / 75 s real MP4s; cap `SHAM_VIDEO_FRAMES` max 2400 = exactly 300 s (5 min).
Changed the default clip length from 16 frames (2 s) to **48 frames (6 s)** — the owner's floor.
`_video_frames()` now clamps to `max(48, min(2400, …))`.
