## Second pass — practical testing found two real bugs (commit 2f030fe, + touch fix)

The directive was to test practically, not just read code. Two real defects came out of running the
stream against the real SQL engine and reasoning about touch events:

1. **`mergeTaskEvents` crashed the chat on first paint.** `listTasks` returns task ROWS with no `events`
   field (only the `thread` op pairs a row with its events). The SSE stream can deliver the first `text`
   event before the thread op has paired them, so `task.events.map(...)` threw `Cannot read properties of
   undefined`. Guarded with `task.events || []`; `lastEventId` guarded too. Covered by
   `liveEvents.test.ts` ("starts a run whose row carries no events yet").
2. **A tap on the desktop clicked twice.** `onTouchStart` fires, then the browser synthesises a `click`;
   both called `clickScreen`, so every touch reached the desktop as a double-click (folders opened, text
   selected). Added a 700 ms `touchAt` ref guard in `GraphicalDesktop.tsx`.

### The real scroll-jump root cause (fixed, commit 9b14d7a)
`src/app/coder-app/_tma/scroll.ts` `useStickToBottom` attached a scroll listener **only when it found a scrollable ancestor** of the feed. In the Telegram webview the **whole document scrolls**, so `scrollParent()` returned null, the effect returned early, and `stick` stayed `true` forever — every live update (SSE `text` events + the 2.5–3 s poll) scrolled the page back to the bottom, i.e. the "screen jumps up inside the chat during real-time responses" the owner reported. Fixed by adding `pageScroller()`/`resolveScroller()`: when there is no inner scroller, read geometry from `document.scrollingElement` and listen on `window`. Regression test `liveFeedScroll.test.ts` extended (page fallback + real-parent-wins) and added to the CI regression list in `.github/workflows/ci.yml`. Also trimmed the computer status line (`FreeComputer.tsx`) which dumped every enabled tool name (owner: redundant fields on the computer page).
