# Plan (draft, not implemented): making the 4B coder strong at complex agentic tasks

Status: proposal for the owner, 2026-10-21. Nothing here takes Kaggle sessions from Sham's notebooks.

## 1. Harness first (no training, biggest win per hour)
Already in the bot: plan → act → verify loop, native tool calls, notes memory, confirmations only for delete / push-or-merge to main.
Next, in this order:
1. **Repo retrieval** — before the first model call, give it the repo tree + the files that match the task (path/keyword match on the
   GitHub tree, then the top N files' heads). Small models fail mostly from guessing files they never read.
2. **Edit by patch, not whole file** — a `github_apply_patch` tool (search/replace blocks) so a 4B model never re-types a 2,000-line file.
3. **Verify for real** — after every write: open a PR from a feature branch, run CI (`github_run_workflow` / `github_ci_status`), feed
   the failing log lines back, loop until green or N tries. Optional free sandbox: GitHub Actions `workflow_dispatch` job that runs a
   command and returns its output (the repo's own runner minutes).
4. **Planner/critic passes** — same model, two extra short calls: "write the plan as a checklist" at the start, "check the diff
   against the checklist" before reporting. Thinking mode (`/think`) only for these passes to keep speed.
5. **Multi-step memory** — keep the checklist + key findings in `notes`; summarise old tool results instead of dropping them
   when the context fills.
6. **Self-consistency on hard steps** — sample 2–3 candidate patches, keep the one whose tests pass.

## 2. Agentic LoRA on tool-use trajectories (commercial licences only)
Rules: no CC BY-NC / NC-SA / research-only sets; no sets generated by GPT-4 / other closed models (their terms forbid training
competitors); check every licence on its card before download and keep a `LICENSES.md` with source + licence + date.
Candidate sources (licence to re-verify on the card):
- Function-calling: `Salesforce/xlam-function-calling-60k` (CC-BY-4.0), `glaiveai/glaive-function-calling-v2` (Apache-2.0).
- Code instructions: `nvidia/OpenCodeInstruct` (CC-BY-4.0), `bigcode/commitpackft` (permissive-only commits).
- Agent tasks: real GitHub issue→fix tasks from SWE-rebench / SWE-bench-extra style sets (CC-BY-4.0) as **tasks only**; the
  trajectories we generate ourselves.
- **Own trajectories (best fit)**: run the bot's own harness with a large **Apache-2.0 open teacher** (e.g. a Qwen3-Coder large model
  through ModelScope API-Inference free calls) on those tasks + the owner's repos; keep only runs whose tests passed
  (rejection sampling), in exactly the bot's tool schema. 3–10k successful trajectories is a realistic first target.
Training: QLoRA r=16–32 on Qwen3.5-4B, 4-bit base, seq 8–16k, 1–2 epochs, loss only on assistant turns + tool calls.
Export: merge → GGUF (llama.cpp `convert_hf_to_gguf.py`) → Q4_K_M → private ModelScope model repo `novaai2026/coder-4b-agent-gguf`
→ set `CODER_MODEL_REPO` / `CODER_MODEL_FILE` on the Studio. Keep the base model as fallback; ship only if the eval below improves.

## 3. Evaluation (decides every release)
A fixed set of 50–100 tasks from the owner's repos + public issue→fix tasks, scored by "CI green after the run", plus tool-call
validity rate and steps per task. Run before and after each LoRA / harness change; never ship a regression.

## 4. Compute that never touches Sham's Kaggle sessions
- **ModelScope Notebook** (same account): free CPU 8 vCPU / 32 GB long-term; one-time 36 h on a 24 GB A10 after binding an
  Alibaba Cloud account (real-name verification, 10 h per session, 1 h idle shutdown). Enough for one or two QLoRA runs on a 4B model.
  (Reported by several sources as of Oct 2026; confirm in the account's Notebook page.)
- **Google Colab free T4** (16 GB, variable session limits) — fine for QLoRA 4B with short sequences; slower.
- **ModelScope API-Inference free daily calls** — for the teacher trajectories (no training compute needed).
- **AMD × ModelScope developer programme** (reported: 100 free MI300X hours on registration) — needs a ROCm stack; check terms.
- Not used: Kaggle (Sham's notebooks own it), Lightning (has Sham workflows), and the free ModelScope programme with hard conditions
  (owner said skip).

## 5. Sham ↔ coder (later, owner decides)
Coder → Sham: Arabic code explanations / task dialogues produced by the coder, entered as a NEW dataset prefix through the engineer's gate
(never `sham-crawl-…`), only after the owner confirms the licence question for Sham's weights. Sham → coder: Sham's Arabic SFT sets that
are not NC (the NC ones such as `hala_sft`, `bactrian_ar` stay out of the commercial coder).
