## 1. لمحة سريعة (Executive Summary)

**شام AI** منصة تبني وتستضيف بوتات تيليجرام متعددة المستأجرين (multi-tenant) تعمل بتوكن كل عميل، بالإضافة إلى أدوات "استوديو" تعمل بالكامل داخل متصفح الزائر. الميزانية صفر دولار. الأولوية المطلقة الآن **ليست البيع للجمهور**، بل تفعيل واختبار حي كامل من طرف المالك (كإدمن) لثلاثة أنظمة: بوت الإعلانات، منظومة المنشآت الطبية، وبوت المتجر — قبل فتح أي بيع عام لخدمات "التفعيل".

---

## 2. الهوية والوضع العام

- **الاسم**: شام AI (Sham AI) / اسم المستودع التقني: Ttbik.
- **المالك**: فرد واحد (مؤسس)، **ميزانية صفر دولار فعلياً** — أي قرار تقني يفترض عدم وجود خدمة مدفوعة (لا Redis/KV مدفوع، لا استضافة فيديو مدفوعة، لا واجهات AI مدفوعة تُستهلك تلقائياً بلا حدود) ما لم يوافق المالك صراحة على تكلفة محددة.
- **المكدّس التقني**: Next.js 14 (App Router) + TypeScript + Tailwind، قاعدة بيانات Supabase (Postgres)، استضافة Vercel، نشر تلقائي من فرع `claude/free-services-marketplace-h6rwk2` في مستودع GitHub `jonsnowx1r-lab/Ttbik`.
- **فريق التنفيذ الحالي**: نموذجا ذكاء اصطناعي يعملان بالتوازي بصلاحية دفع كاملة على نفس الفرع — Claude Code و Grok (xAI) — ينسّقان عبر تعليقات على PR رقم 2 في نفس المستودع (قناة تنسيق فعلية وليست شكلية).

## 3. المبادئ الثابتة غير القابلة للتفاوض

*(محفوظة حرفياً — أي تنفيذ مستقبلي لا يجوز أن يخالفها)*

1. **لا سحب نقدي حقيقي داخل أي بوت تليجرام، إلا استثناءً صريحاً واحداً حدَّده المالك بتاريخ 2026-08-29 لبوت الإعلانات تحديداً.** لكل بقية البوتات (متجر، صيدلية/منشآت طبية، وأي بوت قادم): أي "محفظة" أو "رصيد" هو نظام **إيداع فقط**. النقاط تُستخدم **داخل البوت فقط** ولا تتحول أبداً مرة أخرى إلى نقد حقيقي. **أي تنفيذ للسحب في بوت الإعلانات يحتاج تصميم امتثال/حدود فعلي (KYC بسيط، حدود مبالغ، سجل مراجعة) قبل الإطلاق الفعلي**؛ يُطرح على المالك كنقطة تصميم قبل التنفيذ (انظر 7.3).
2. **لا نبيع "وصولاً" لأدوات ذكاء اصطناعي عامة، ولا نبيع كوداً كملف يُسلَّم للعميل.** أي فكرة يمكن لأي شخص الحصول على نفس نتيجتها بمحادثة مجانية مع أي AI خلال دقيقة تُرفض تلقائياً مهما كان سعرها منخفضاً.
3. **نماذج البيع المقبولة فقط (لا ثالث لها)**: جمهور/قناة مملوكة فعلياً · بوت تليجرام يعمل فعلياً بتوكن العميل نفسه (مستضاف ومُدار من عندنا) · أداة استوديو حقيقية تعمل بالكامل في متصفح الزائر (نمط `StudioGate`) · أداة عمل عام (Done-For-You) منفَّذة فعلياً من طرفنا.
4. **قاعدة قبول أي فكرة منتج جديدة**: هل الناتج النهائي شيء نملكه/ننفّذه نحن فعلياً، أم مجرد نص/كود يستطيع أي أحد الحصول عليه مجاناً من AI؟ — يُرفض الخيار الثاني تلقائياً.
5. **كل تعديل على قاعدة البيانات الحية يمرّ عبر ملف واحد فقط**: `supabase/pending_migration.sql`.
6. **درس GRANT/RLS**: أي جدول جديد يحتاج `grant select, insert, update, delete on <table> to service_role;` صراحة، وإلا `permission denied`.
7. **الاستخدام الأساسي لأدوات الاستوديو المجانية يبقى مجانياً فعلاً.**

## 4. السياق التاريخي — ملخّص

1. **رُفض قطعياً**: بيع "وصول لأدوات AI عامة" وبيع أكواد بوتات جاهزة كملف.
2. **رُفض أيضاً**: "أعلن في قناتنا" (مراسلة يدوية) و"بوت مساحات إعلانية" (كود عليه سعر).
3. **التصميم المعتمد**: بوت تيليجرام يعمل بتوكن العميل فعلياً عبر قالب في الموقع — نمط White-label bot builder + Dispatcher موحّد.
4. **نمط ثانٍ مقبول**: أدوات "استوديو" تعمل بالكامل في متصفح الزائر بلا خادم وبلا AI.
5. **التنفيذ الفعلي حتى الآن**: `hosted_bots`, webhook موحّد `/api/bots/hook/[botId]`, ثلاثة قوالب (`ad-campaign`, `store`, `clinic`), بوابة دفع بـ`orderCode`, مشاهدة إعلان → مكافأة (منع مزدوج)، تحقق عضوية قناة، حضور يومي، متصدرون، إحالات، بث جماعي، سجل تدقيق `bot_wallet_tx`.

## 6. خطة التنفيذ المرحلية

**القاعدة الحاكمة**: لا خدمة "تفعيل بوت" للبيع العام قبل اكتمال المراحل 1–3 حياً تحت إشراف المالك المباشر.

### المرحلة 0 — تجهيزات أساسية
0.1 كل تعديل DB في `pending_migration.sql` فقط. 0.2 GRANT صريح لأي جدول جديد. 0.3 أرشفة الهجرات (اختياري، 10.6). 0.4 مراجعة كل PR بقراءة الـdiff الفعلي كاملاً.

### المرحلة 1 — تفعيل بوت الإعلانات (للإدمن فقط)
بوت حي بتوكن حقيقي للمالك، حملة إعلانية حقيقية واحدة على الأقل عبر `/admin/bots/[id]/ads`، اختبار دورة كاملة (عرض → مطالبة → منع مزدوج → تسجيل تدقيق)، حضور يومي/متصدرون/إحالات/بث. **لا يُبنى السحب بعد** (مؤجَّل للمرحلة 4، رهن القسم 7.3).

### المرحلة 2 — منظومة المنشآت الطبية (صيدلية/مشفى/مستوصف/نقطة طبية)
بناء جديد كامل (ليس امتداداً للقالب الحالي). **2.أ** موقع جغرافي هرمي (محافظة←مدينة←ناحية←قرية) — رهن سؤال 7.1. **2.ب** تسجيل منشأة بتحقق يمنع التكرار/التزييف — رهن سؤال 7.2. **2.ج** قسم "المناوبة" للمستخدم بتوقيت دقيق وحجز. **2.د** موافقة/رفض/اقتراح بديل من صاحب المنشأة. **2.هـ** نفس التدفق العام لكل الأنواع (مرونة في عدد المسؤولين لكل منشأة، انظر تصحيح 9.3).

### المرحلة 3 — توسعة بوت المتجر ✅ (منفَّذة، انظر "حالة التنفيذ" أعلاه)
إضافة متجر للتاجر، تسوّق، بيع مستعمل، شراء مستعمل.

### المرحلة 4 — نموذج المحافظ لكل بوت وللموقع
متجر/منشآت طبية: إيداع فقط. بوت الإعلانات: إيداع **و**سحب (استثناء صريح، رهن ضوابط الامتثال 7.3). الموقع نفسه: نظام الطلبات الحالي فقط، لا قرار بمحفظة على مستوى الموقع.

### المرحلة 5 — بوابة الإطلاق العام
لا تبدأ قبل اكتمال 1–3 حياً بلا أخطاء: تحديد أسعار التفعيل، ربطها بنظام `services`+`orderCode`، فتح تدريجي (نوع بوت واحد أولاً)، مراجعة يدوية للتسجيلات الجديدة حتى تثبت آلية التحقق نفسها.

## 7. أسئلة تصميمية مفتوحة — بانتظار إجابة المالك

### 7.1 كيف يُحدَّد "بلد"/موقع المستخدم؟
مُعرِّف تيليجرام وحده لا يحمل بلداً موثوقاً. مُقترَح 10.1: زر مشاركة رقم الهاتف (`request_contact`) يعطي رمز الدولة الدولي بضغطة واحدة + تعديل يدوي احتياطي.

### 7.2 آلية التحقق من هوية الصيدلاني/مسؤول المنشأة
مثال أولي: رقم ترخيص نقابة + مراجعة يدوية من الإدمن (نفس نمط موافقة الطلبات القائم).

### 7.3 ضوابط الامتثال لسحب بوت الإعلانات
حدود المبالغ، شكل التحقق من الهوية، سجل المراجعة اليدوي، حد أدنى لعمر الحساب/النقاط قبل أول طلب سحب.

1. إشارة ترقيم غير متطابقة بين نسخ الملف — المقصود دوماً "البند 1" (منع السحب).
